## Context

Мотивация — `proposal.md`. Библиотека — IndexedDB `amo-stickers` версии 1 (`db.ts`): хранилища `packs` (`Pack`: `id`,
`title`, `source`, `sourceRef?`, `coverId?`, `createdAt`, `usedAt?`) и `stickers` (`StickerRec`: `id`, `packId`,
`blob`, `width`, `height`, `emoji?`, `caption?`, `createdAt`; порядок в паке — по `createdAt`). Id стикера Telegram —
`tg:<file_unique_id>`, своего — `uid()` (base36), id пака — `tg:<имя набора>` или `custom`. `deleteSticker` не чистит
`coverId` пака: обложка может указывать на удалённый стикер (`db.types.ts`: тогда обложка — первый стикер). У подписи
своего стикера лимита длины нет.

Импорт из Telegram (`importTelegramSet`) пишет стикер за стикером и откатывается по снимку записей; ход, отмену и исход
в UI ведут `usePackImport` и чистый `runPackImport/`, удержание — причина `import`, переход к паку после успеха — только
при открытом экране «Добавить стикеры» (`finishImport/`). Экран «Добавить стикеры» — два сегмента (`AddSegment`), футер
зависит от сегмента (`AddView`). Меню пака — `SectionHeader/` (`headerAction(sectionId)`: у `custom` действий нет).
Код работает в чужой странице в двух окружениях; зависимостей в бандле ради этой задачи не добавляем (решение
пользователя).

## Goals / Non-Goals

**Goals:**

- выгрузка и загрузка без библиотек, без сети и без API расширения — один код для расширения и userscript;
- загрузка «всё или ничего»: никакой частично записанной библиотеки при битом файле, отмене, квоте, закрытии вкладки;
- любой файл, выгруженный amo stickers, читается: выгрузка не пишет того, что отклонит чтение;
- память при загрузке stored-архива не растёт с размером файла: GIF читаются по одному срезами `File`;
- формат с версией и запасом на будущее: неизвестные поля игнорируются.

**Non-Goals:**

- выбор паков для загрузки (импортируются все паки файла);
- перенос недавних, настроек, режима попапа;
- zip64, шифрование, многотомные архивы, самораспаковывающиеся архивы, сжатие при выгрузке;
- отмена уже начатой записи в базу;
- синхронизация между браузерами, облако, ссылка на файл.

## Decisions

### 1. Формат: zip без сжатия, своя упаковка

```
<имя>.amostickers  (zip, метод 0 — stored)
├─ manifest.json
└─ stickers/<номер>.gif
```

```jsonc
{
  "format": "amo-stickers",          // признак формата
  "version": 1,                      // целое; чтение принимает 1…FORMAT_VERSION
  "packs": [
    {
      "id": "tg:Gachi",              // `custom` или `tg:<имя набора>`
      "source": "telegram",          // telegram | custom
      "title": "Gachi",
      "sourceRef": "Gachi",          // необязательно; только у telegram, равен имени из id
      "createdAt": 1750000000000,    // только в выгрузке библиотеки
      "usedAt": 1755000000000,       // только в выгрузке библиотеки, если есть
      "coverId": "tg:AgAD…",         // необязательно; только id стикера этого пака из файла
      "stickers": [
        { "id": "tg:AgAD…", "file": "stickers/0.gif", "emoji": "😀" },
        { "id": "lq3k9a1z…", "file": "stickers/1.gif", "caption": "привет" }
      ]
    }
  ]
}
```

- Порядок стикеров — порядок массива, `createdAt` стикера не выгружается: при загрузке порядок задаётся заново.
- `width` и `height` не выгружаются — при загрузке берутся из заголовка GIF (`gifScreenSize`), а не из недоверенного
  описания.
- Порядок паков в массиве — порядок ленты (`orderPacks` без снимка), «Мои стикеры» первыми.
- `createdAt` и `usedAt` пака пишутся только в выгрузке библиотеки (спека «Состав файла»): выгрузка одного пака уходит
  другим людям и не раскрывает, когда из пака отправляли. Времени выгрузки (`exportedAt`) в файле нет — оно ничему не
  служит.

**Почему zip stored, а не JSON с base64:** файл на треть легче, GIF читаются срезами `File.slice` без загрузки файла в
память, архив открывается архиватором. **Почему без библиотеки:** stored-запись — заголовки и CRC-32 (~150 строк
вместе с чтением), а GIF и так сжаты — deflate ничего не даст. Чтение deflate (метод 8) — через
`DecompressionStream('deflate-raw')` браузера: пересжатый архиватором файл тоже читается, кода почти не прибавляется.
Другие методы у записей, на которые ссылается описание, — ошибка битого файла.

**Расширение `.amostickers`** — решение пользователя: файл не спутать с обычным архивом, диалог фильтрует свои файлы.
Узнавание — по содержимому: конец центрального каталога zip и `manifest.json` с `format: "amo-stickers"`; `accept`
поля — `.amostickers,.zip`, `file.type` не проверяется (у незнакомого расширения он пуст).

**Версия:** `version` — целое. Чтение принимает `1…FORMAT_VERSION`; больше — ошибка «файл новее, обновите amo
stickers». Новое необязательное поле не поднимает версию (неизвестные поля игнорируются); версия поднимается только
при несовместимой смене, и тогда чтение старых версий остаётся в коде.

**Пределы формата** (одни константы для выгрузки и чтения, `libraryFile/limits.ts`):

| Что | Предел | Нарушение на чтении | На выгрузке |
|---|---|---|---|
| стикеров в файле | 10 000 | ошибка «слишком большой файл» | ошибка с советом выгружать по пакам |
| размер файла | < 4 ГиБ (zip32) | то же | то же |
| GIF (распакованный) | 8 МБ | ошибка битого файла | GIF больше 8 МБ в базе — ошибка выгрузки с названием пака* |
| `manifest.json` | 16 МБ | ошибка файла | не достигается: 10 000 × строки в пределах ниже ≈ 10 МБ |
| `title` | 128 графем | урезается | урезается |
| `caption` | 200 графем | урезается | урезается |
| `emoji` | 16 графем | урезается | урезается |

\* Стикеры в базе не больше 2 МБ, кроме последней ступени лестницы конвертации; 8 МБ на практике не достигается, но
проверка на выгрузке оставляет обещание «свой файл читается» честным.

Урезание по графемам — `Intl.Segmenter`, как `sanitizeLabel` в `fileName.ts`. Метка имени отправляемого файла и так
не длиннее 32 графем, поэтому урезанная подпись отправляется с той же меткой.

### 3. Чтение zip

Только из `Blob` по срезам; ни одно смещение не читается без проверки против `file.size`.

1. **EOCD** — с конца файла в последних 65 535 + 22 байтах; кандидат по сигнатуре принимается, только если длина
   комментария из него ровно доводит до конца файла. Многодисковый архив и zip64 (поля `0xFFFF` / `0xFFFFFFFF`) —
   ошибка битого файла. Архив, перед которым дописаны данные (смещения каталога не сходятся с позицией EOCD), — ошибка
   битого файла: самораспаковывающиеся архивы — не наш случай.
2. **Центральный каталог** — целиком в пределах файла, число записей ≤ 10 000 + запас на служебные (ошибка «слишком
   большой файл» сверх 20 000), повтор имени — ошибка битого файла. Имена: UTF-8 (флаг 11) или CP437 — для сопоставления
   нужны только ASCII-имена наших записей; имя с `..`, `\`, началом с `/` или буквой диска — запись пропускается (на неё
   нельзя сослаться).
3. **Корень описания**: `manifest.json` в корне, иначе `<папка>/manifest.json` для единственной папки верхнего уровня
   без учёта `__MACOSX/`; `file` стикеров разрешается от каталога описания. Записи-папки (имя на `/`), `__MACOSX/…`,
   `.DS_Store` и записи, на которые описание не ссылается, не читаются и не проверяются — их метод и размер не важны.
4. **Данные записи** — смещение данных считается по длинам имени и extra **локального** заголовка (у архиваторов они
   расходятся с центральным каталогом), размеры и CRC — из центрального каталога (локальный заголовок с data
   descriptor, бит 3, несёт нули). Метод 0: сжатый размер равен несжатому, иначе ошибка; данные — срез `Blob`.
   Метод 8: `DecompressionStream('deflate-raw')` с обрывом, как только выход превысил несжатый размер из каталога или
   лимит GIF (zip-бомба). Конец данных записи — в пределах файла и не заходит на другую запись.
5. **Целостность** — CRC-32 прочитанных байтов каждой записи, на которую ссылается описание (и stored, и deflate),
   сверяется с центральным каталогом; расхождение — ошибка битого файла. Порчу внутри LZW-данных GIF `inspectGif` не
   видит, raw deflate тоже — без CRC сценарий «Битый GIF» держался бы на удачной фикстуре.

### 4. Загрузка: описание → проверка стикеров → одна транзакция

**Описание и карточка** (`readLibraryFile`) — без записей в базу и без чтения GIF:

1. zip по п. 3, `manifest.json` ≤ 16 МБ, `JSON.parse` и гарды. Пак: `source` и `id` согласованы (`custom` ↔ `id ===
   'custom'`; `telegram` ↔ `id === 'tg:' + имя`, имя по `SET_NAME_RE`, `sourceRef`, если есть, равен имени), строки
   урезаются по пределам, `createdAt` / `usedAt` — конечные неотрицательные числа или отсутствуют. Стикер: у пака
   Telegram id `tg:[A-Za-z0-9_-]{1,64}`, у своего — `[a-z0-9]{1,32}` без префикса `tg:`; `file` — строка, разрешимая в
   запись архива. Повтор id пака или стикера в файле, повтор ссылки на один `file` — ошибка файла. `coverId`, который не
   указывает на стикер этого пака из файла, отбрасывается без ошибки (у пака из Telegram обложка может указывать на
   удалённый стикер). Паки без стикеров отбрасываются.
2. Сверка с базой (`listPacks`, ключи стикеров): стикер, id которого уже есть в базе (в этом паке или в другом), — не
   новый; пак, который есть, — запись пака не трогается. Карточка — паки, стикеров в файле и новых, итог: новые паки
   (без `custom`) и новые стикеры; «Мои стикеры» — строкой «добавится N». Сверка повторяется при возврате на сегмент
   «Файл» и при нажатии «Импорт» (дёшево, без чтения GIF).

**Проверка стикеров** (`prepareImport`, по «Импорт»): для каждого нового стикера — данные по п. 3.4–3.5, `inspectGif`,
стороны из `gifScreenSize`, прогресс «N/M», `signal` перед каждым стикером. В план попадает `Blob` с типом `image/gif`:
для stored — срез `File` (данные не копируются в память), для deflate — распакованные байты. Отмена — выход до
транзакции.

**Запись** (`writeImport`) — одна транзакция IndexedDB, в которой нет ни одного `await` не-IDB операции (иначе она
закоммитится сама): все решения принимаются в колбэках `onsuccess` запросов той же транзакции.

1. `getAll` паков и `getAllKeys` стикеров (или `get` по каждому id) — состояние базы в момент записи.
2. Для каждого пака плана: стикеры, id которых уже заняты, выбрасываются; если не осталось ни одного — пак пропускается.
   Пака в базе нет — `put` записи пака: `title`, `sourceRef`, `createdAt` (из файла или `startedAt`), `usedAt` (из
   файла, если есть), `coverId` (из файла, если он в оставшихся стикерах, иначе первый из них); для `custom` — та же
   форма, что `ensureCustomPack` (`createdAt: 0`, название по языку создания), но запросом этой транзакции, а не вызовом
   функции. Пак есть — запись пака не пишется.
3. `createdAt` новых стикеров пака — после всех его стикеров: база — `max(createdAt стикеров пака в базе) + 1` (через
   индекс `packId` в той же транзакции), для нового пака — `startedAt`; к базе прибавляется номер стикера в порядке
   файла. Отсчёт от `Date.now()` не гарантировал бы «в конец»: прошлый импорт файла мог дать стикеры с `createdAt` до
   `startedAt + 10 000`, а часы — уйти назад.
4. `put` стикеров. Исход — промис по `oncomplete`; `onerror` / `onabort` (квота, закрытие вкладки) — отказ, и база как
   до импорта. Ответ — что реально записано (паки и число стикеров) — для статуса и перехода.

Атомарность даёт сама база, поэтому снимок и откат, как у Telegram, не нужны. Отмены записи нет: после выдачи запросов
транзакция переходит к коммиту, и `abort()` бросил бы `InvalidStateError`, а стикеры всё равно записались бы. Поэтому
на время записи «Отменить» недоступна, а в карточке и, когда сегмента не видно, в статусе — «Запись…» (спека «Прогресс
и отмена импорта файла»). Запись хода не сообщает, поэтому статус обновляется и по уходу с сегмента и возврату на него
(`fileImportStatus`), а не только по началу этапа.

**Альтернатива — запись по стикеру с откатом, как у Telegram.** Отвергнута: откат после сбоя по квоте сам может упасть
по квоте, а закрытие вкладки посреди импорта оставило бы полупак, что нарушает спеку.

### 5. Выгрузка

`exportLibrary({ packId? })` — паки по порядку ленты или один пак, их стикеры (`listStickers`), манифест, затем zip:
`Blob` из частей ссылается на блобы стикеров без копии, а CRC-32 считается по одному GIF за раз с уступкой потока
(`await` между стикерами), ход — в статусе. До сборки — пределы п. 1 (число стикеров, размер, вес GIF), строки
урезаются, `coverId` пишется, только если такой стикер есть в паке. Готовый манифест прогоняется через гарды чтения до
сборки архива: выгрузка не может сохранить то, что не прочитает (тест — круговой, с удалённой обложкой и длинной
подписью). Пак Telegram без `sourceRef` выгружается без него — после загрузки у него так же нет «Копировать ссылку».
Выгрузка ничего не пишет в базу и не трогает `usedAt` и недавние.

Имя файла (`exportFileName`) — `packTitle(pack)`: снять символы `\p{Cc}` и `\p{Bidi_Control}` (те же классы, что в `LABEL_JUNK`
`core/fileName.ts`, но без точки: она допустима в названии), заменить `\ / : * ? " < > |` на `_`, снять точки и пробелы в начале (имя с точки в macOS и Linux — скрытый файл; до урезания, чтобы они не съели предел), урезать до 100 графем, снять точки и пробелы в конце; пустое
имя и зарезервированные имена Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1…9`, `LPT1…9` без учёта регистра) — запасное
`amo-stickers`; расширение `.amostickers`. Библиотека — `amo-stickers-<YYYY-MM-DD>.amostickers` по местной дате.

### 6. Состояние в провайдере, удержание, взаимоисключение

- `useLibraryExport` в провайдере: одна выгрузка за раз (`exportingRef`), признак `isExporting` для «Выгрузить
  библиотеку» и пунктов «Выгрузить пак»: состояние в компоненте сегмента или меню не пережило бы «Назад», закрытие меню
  и виртуализацию ленты, и вторая выгрузка шла бы параллельно (и Chrome спросил бы о нескольких скачиваниях). Причина
  удержания — новая `export` в `HoldReason` (не из `PANEL_REASONS`: переживает закрытие попапа, как `import`).
- `useFileImport` в провайдере, как `usePackImport`: файл, карточка, ошибка, этап (`checking` / `writing`), ход,
  `AbortController`. Общий признак «идёт импорт» обоих хуков — одна причина удержания `import` и `isImportDisabled`
  обоих сегментов.
- Исход импорта файла — чистая функция по образцу `runPackImport/` и `finishImport/`: успех — статус «Добавлено
  стикеров: N», сброс файла, `scrollToSection(первый по порядку ленты раздел с добавленными стикерами, 'instant')`,
  только если открыт экран «Добавить стикеры» (`scrollToSection` закрывает экран и переключает режим); отмена — «Импорт
  отменён»; ошибка — у зоны, если открыт сегмент «Файл», иначе в статусе (`importErrorTarget` получает сегмент
  параметром); после ошибки проверки «Импорт» недоступна до другого файла, после ошибки записи — доступна. Паки
  перечитываются (`refreshPacks`) по снимку порядка, как после импорта Telegram.

### 7. UI сегмента «Файл»

- Вкладка `file` третьей в `role="tablist"`; подписи «Telegram», «Свой стикер», «Файл» / «Telegram», «Custom
  sticker», «File» — ширина на 350 px проверяется на стенде.
- Тело: зона загрузки (вид как `DropZone/` своего стикера, наименьшая высота — та же `h-31`: иконка, текст о
  перетаскивании, «Выбрать файл»; удержание `fileDialog` по нажатию). Карточка файла встаёт на место зоны, как превью
  своего стикера: `FileDropZone` получает её слотом `card` и показывает строкой сверху имя файла (`truncate`) и
  маленькую «Заменить файл» в правом углу, под ними — карточку (`aria-busy` пока читается, список паков с `truncate`,
  итог, ход импорта — полоса с `aria-valuetext`, «Запись…»). Перетаскивание принимает вся зона в обоих видах. Ошибка с
  `role="alert"` — под зоной: ошибка чтения без карточки, ошибка записи — под зоной с карточкой. Футер вне прокрутки.
- Высота зоны с карточкой — по содержимому, от `min-h-31` до свободного места тела экрана; дальше список паков
  прокручивается внутри карточки (`feed-scroll`; фокус с клавиатуры даёт браузер, пока список есть куда прокручивать;
  край со скрытыми строками затухает маской `scroll-fade` по scroll-driven анимации — без замера скриптом),
  а имя файла с «Заменить файл» и итог или ход — на виду. Раскладкой, без замера: на сегменте «Файл» тело экрана —
  колонка flex (`Screen` с `shouldFitBody`), выбранная форма, её блок полей и панель `FileTransfer` — колонки с
  `grow` без `min-h-0`, вкладки, заголовок и ошибка — `shrink-0`, зона — `basis-31 grow max-h-max min-h-31`, внутри
  неё подложка и карточка — `flex-1 min-h-0`, список — `min-h-0 overflow-y-auto`. Колонки растут в свободное место
  тела, а делит его только зона: от основы в наименьшую высоту до высоты содержимого; список сжимается внутри неё,
  потому что высота зоны определена для её детей. Наименьшая высота колонок — по основам их детей, то есть заголовок,
  зона в наименьшую высоту и ошибка: ниже колонки не сжимаются, и не поместившееся прокручивает тело, а не уходит под
  строку статуса. Отступ тела под строку статуса (`--status-inset`) и ошибка записи уменьшают свободное место — зона
  сжимается до наименьшей высоты; прокрутка тела наступает, только когда и этого мало: ошибка записи под показанной
  строкой статуса (замер на стенде: RU — 5 px под строкой в одну строку и 23 px под строкой в две, EN — 7 px под
  строкой в две). Колонки с `min-h-0` отброшены: они сжимались ниже содержимого, и ошибка под строкой статуса в две
  строки уходила под неё на 11 px без прокрутки тела. Остальные сегменты и «Настройки» — тело блоком: колонка у формы
  с телом-блоком высоты не меняет, и длинное содержимое прокручивает тело. Замер скриптом (`ResizeObserver` тела и
  высоты над зоной) отброшен: раскладка решает то же без лишнего кадра между сменой содержимого и высотой зоны.
  Постоянная высота `h-31` отброшена по замечанию пользователя: при 9 паках список прокручивался с трёх строк, а под
  зоной оставалось ~90 px пустого места.
- Выгрузка библиотеки — в «Настройках», группой «Библиотека» последней, после «Telegram» (`SettingsView/LibraryExport/`:
  пояснение, кнопка `secondary` «Выгрузить библиотеку» с ходом или «нет стикеров» рядом, `shouldKeepFocus`; без
  стикеров и во время любой выгрузки — недоступна; под кнопкой — ссылка «Загрузить из файла» на сегмент «Файл»).
  Группа вне формы настроек: полей у неё нет. На сегменте «Файл» — только ссылка «Выгрузить библиотеку» в строке
  заголовка «Загрузка из файла» (`LinkButton/` — вид ссылок подсказок, без новой строки по высоте). Почему не на
  сегменте: группа выгрузки (100–117 px) не давала сегменту поместиться в панель 350×400 без прокрутки тела (видимая
  высота 275 px). Экспорт ищут рядом с импортом, и экспорт данных обычно лежит в настройках (Firefox «Импорт и резервные
  копии», Chrome «Импорт/экспорт закладок», выгрузка данных Telegram и Slack) — поэтому ссылки в обе стороны.
- Ссылка с сегмента открывает «Настройки» с фокусом на кнопке: `openScreen('settings', { focus: 'libraryExport' })`
  кладёт цель в `usePickerView` (`screenFocus`), а `useScreenFocus` при монтировании экрана ищет её по id
  (`SCREEN_FOCUS_ID`), ставит фокус без прокрутки браузера и прокручивает тело к группе цели по геометрии
  (`focusScrollTop`: вся группа, иначе хотя бы цель; без нижнего отступа тела под строкой статуса) — `scrollIntoView` и
  прокрутка по фокусу задели бы страницу amo. Без цели — первое поле, как прежде. Флаг пропом через несколько уровней
  отброшен: цель — свойство перехода, и её знает точка входа.
- Футер: «Импорт» / «Отменить» — тот же `Button` без `key`, `isRepeatClick/` против второго клика, как
  `TelegramImportFooter/`; переиспользовать его с пропом недоступности «Отменить» на этапе записи.
- Фокус при открытии сегмента «Файл» — на его вкладке: текстового поля нет, и `useScreenFocus` ставит фокус на вкладку
  выбранного сегмента.
- Фокус после импорта не падает в `body`: переход к ленте закрывает экран вместе с «Импорт», и фокус встаёт на вкладку
  раздела (`scrollToSection` с `shouldFocusTab`); если экран остался, а «Импорт» стала недоступна, — на вкладку «Файл»
  (`useImportEndFocus`). Только если фокус потерян (`isFocusLost`): ушедший в поле amo его не теряет.

### 8. Строки

Ключи групп `add.segment.file`, `add.file.*`, `settings.group.library` и `settings.library.*` (группа «Библиотека»
«Настроек»), `pack.export` (рядом с `pack.copyLink` и `pack.delete`; `pack.menu` уже занят именем меню), `status.export*`, `status.fileImport*`, `error.libraryFile.*` — парами в `RU` и `EN`. Ошибки
чтения — `new Error(t(…))` в момент броска (не константы модуля).

## Risks / Trade-offs

- [Blob URL из content script расширения может не скачаться со страницы amo] → проверить на стенде и в живом amo в
  обоих окружениях первым делом (задача 1.1). Если не скачивается — запасной путь: передать `Blob` агенту мира
  страницы через `pageBridge` и кликнуть ссылку там; спека от этого не меняется. **Проверено (1.1)** в headless Chrome 153: каталог загрузок задан CDP
  `Browser.setDownloadBehavior`, у каждой загрузки событие `Browser.downloadProgress` — `completed`, а файл лежит в
  этом каталоге полного размера. Блоб из изолированного мира content script получает адрес с источником страницы
  (`blob:https://web.dev.amo.tm/…`).
  - Стенд, мир страницы (userscript без менеджера): `page-world Котики.amostickers`, 3 145 728 B.
  - Стенд, content script расширения: `content-script Мои стикеры.amostickers`, 3 145 728 B.
  - `web.dev.amo.tm` (страница входа), мир страницы: `page-world Котики.amostickers`, 3 145 728 B.
  - `web.dev.amo.tm` (страница входа), content script расширения: `content-script Мои стикеры.amostickers`,
    3 145 728 B; без жеста пользователя (вызов через 2 с, как после сборки архива) — `no-gesture.amostickers`, 4 B.
  - Userscript с менеджером (Tampermonkey, `@sandbox DOM` / `@inject-into content`) — **не проверено агентом**:
    менеджер не ставится в headless-профиль. Его мир — изолированный того же вида, что у content script, где
    скачивание работает. Проверка — в G9 (6.3) или пользователем.

  Запасной путь через агента для проверенных окружений не нужен.
- [Срез `File` в IndexedDB: если файл на диске изменят между проверкой и записью, в базу уйдут другие байты] → риск
  принят: окно — секунды, источник — действие самого пользователя. Альтернатива — копия байтов в память — вернула бы
  рост памяти с размером файла.
- [Пересжатый архиватором (deflate) файл держит в памяти распакованные GIF до транзакции — всю добавляемую часть
  библиотеки] → принято: свой файл (stored) читается срезами, пересжатие — редкий ручной случай; память ограничена
  числом и весом стикеров (п. 1).
- [Одна большая транзакция на сотни мегабайт] → Chrome пишет блобы на диск; проверить на библиотеке ~500 МБ (задача
  6.2). Если окажется тяжело — транзакция на пак, но это ослабляет требование о закрытии вкладки (спека «Прогресс и
  отмена импорта файла»: «всё или ничего»), поэтому такой переход — только с правкой спеки и согласия пользователя.
- [Пропуск стикера, id которого занят в другом паке, меняет число добавленных] → карточка считает новые после сверки,
  запись повторяет сверку и возвращает реально записанное — статус показывает его.
- [Своя упаковка zip — свой парсер недоверенного формата] → п. 3: смещения и длины против размера файла, лимиты до
  чтения, CRC, обрыв распаковки; тесты на обрезанный, перекрытый, дописанный спереди файл и zip-бомбу.
- [Длинные списки паков в карточке на 350×400] → карточка на месте зоны, зона растёт до свободного места тела экрана,
  дальше список паков прокручивается внутри неё, имя файла и итог на виду, футер вне прокрутки.

## Migration Plan

Схема IndexedDB не меняется, миграции нет. Откат — revert PR: файлы `.amostickers` остаются у пользователей и
читаются следующей версией с этим кодом.
