## Context

Чтение тела с лимитом уже есть: `readLimited` и `readResponseLimited` в `core/net.ts` для `fetch` (service worker и
userscript без менеджера), обрыв по `Content-Length`, `onprogress` и `onload` в `gmNetwork.ts`. JSON и тело ошибки
этим путём не идут.

## Decisions

### 1. Лимит JSON — 2 МБ, одна константа в ядре

`MAX_JSON_BYTES = 2 * BYTES_IN_MB` в `core/net.ts` рядом с `MAX_REMOTE_GIF_BYTES`. Самый большой реальный ответ —
выдача GIPHY на 24 элемента со всеми версиями и `getStickerSet` на 120 стикеров — порядка сотен КБ, запас на порядок.
Лимит не параметр `fetchJson`: контракт `HostNetwork` не меняется, и все окружения берут одно значение.

Ошибка — `tooBigError(MAX_JSON_BYTES)`, «Файл больше 2 МБ». Слово «файл» для ответа API неточно, но issue требует
тот же текст, а новый ключ словаря ради ответа, которого в жизни не бывает, не окупается.

- *Альтернатива — `maxBytes` параметром `fetchJson`*: отпадает — у всех вызовов было бы одно значение.

### 2. JSON для `fetch` — `readJson(res)` в `core/net.ts`

`readResponseLimited(res, MAX_JSON_BYTES)` → `TextDecoder` → `JSON.parse`. Общая функция для service worker и
`fetchNetwork`, чтобы лимит и разбор не расходились. `TextDecoder` снимает BOM так же, как `res.json()`.

### 3. Тело ошибки — префикс потока

`readPrefix(stream, maxBytes)` читает поток, пока не наберёт `maxBytes`, и отменяет источник — без ошибки: это не
превышение, а «больше не нужно». `fetchChecked` берёт тело ошибки через `readErrorBody` — `readPrefix` на
`ERROR_BODY_MAX_BYTES = ERROR_BODY_PREVIEW * 4` байт: 200 символов UTF-8 занимают не больше 800 байт, поэтому символ,
разрезанный на границе чтения, лежит за 200-м и в текст ошибки не попадает. Сбой чтения тела — пустая строка, как и
раньше: HTTP-ошибка важнее тела.

`readLimited` собран поверх `readPrefix`: читает `maxBytes + 1` байт, и лишний байт — признак превышения. Цикл чтения
потока один на оба режима; читается и отменяется то же, что в отдельном цикле с ранним броском: кусок, на котором
случилось превышение, прочитан в обоих.

### 4. `gmNetwork`

- `fetchJson` — `send(…, 'text', MAX_JSON_BYTES)` вместо `NO_LIMIT`.
- На `onload` размер текстового тела проверяется так же, как `arraybuffer`: в байтах UTF-8 (`TextEncoder`), иначе
  ответ без `Content-Length` и без `onprogress` прошёл бы любой длины.
- Не-2xx: в `onprogress` загрузка обрывается, как только пришло больше 800 байт, с `httpError` по тому, что успело
  прийти. На заголовках по `Content-Length` тело ошибки не обрывается: менеджер ещё не отдал ни байта, и текст ошибки
  остался бы без начала тела; обрыв на заголовках — как и сейчас, только по `maxBytes`.

Менеджер без `onprogress` дочитает тело ошибки целиком — это его буфер, повлиять на него нечем, кроме `Content-Length`.

## Risks / Trade-offs

- [ответ API честно вырос больше 2 МБ] → поиск или импорт падают «Файл больше 2 МБ»; лечение — поднять константу.
  Запас на порядок от наблюдаемых размеров.
- [менеджер не зовёт `onprogress`] → тело ошибки дочитывается целиком, как сейчас; JSON обрывается на заголовках или
  проверяется на `onload`.
- [менеджер зовёт `onprogress`, но не кладёт в него уже пришедший текст] → тело ошибки больше 800 байт обрывается, и
  текст ошибки — `HTTP <код> ` без начала тела. Статус остаётся, и `httpStatus` его разбирает; тот же обрыв по ходу
  загрузки уже действует для ошибок больше `maxBytes`. Не проверено, отдают ли Tampermonkey и Violentmonkey частичный
  `responseText` у text-запроса в `onprogress`.
