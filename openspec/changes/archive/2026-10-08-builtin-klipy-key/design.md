## Context

Мотивация — `proposal.md`, требования — `specs/`. Образец — встроенный токен Telegram-бота (архив
`2026-10-04-builtin-telegram-token`): `define` `__TELEGRAM_BOT_TOKEN__` в `build.mjs`, проверка формата
`scripts/telegramToken.ts`, единственный читатель константы `src/core/builtinToken.ts`, выбор токена и разбор отказа
рядом с запросами (`sources/telegram.ts`), подпись и подсказка поля по наличию встроенного (`telegramTokenText/`).

Что есть в поиске GIF сейчас:

- `availableFeeds(settings)` (`sources/gifs.ts`) даёт `klipy` только при `settings.klipyKey`; `useFeedChoice` берёт из
  него список источников, пустой список — пустое состояние `gifs.noKeys` в `GifView`.
- `fetchGifs(host, settings, feed, …)` передаёт `klipyKey` в `klipy()`, который зовёт `host.fetchJson`. Ошибка уходит в
  `useGifFeed` и показывается `status.gifFailed` («GIF: {message}») и, на пустой ленте, `gifs.loadFailed`.
- Не-2xx ответ во всех окружениях — `httpError(status, body)` с текстом `HTTP <код> …`; статус из текста разбирает
  `httpStatus` (`core/net.ts`). Статусы отказа ключу KLIPY — `KEY_REJECT_STATUSES.klipy` (401, 403, 404).
- `SettingsView` рисует поле KLIPY с литеральной подписью «KLIPY API key», подсказкой `settings.klipy.where` и
  пояснением группы `settings.gif.oneKey`; проверка у поля — `checkGifKey` по сохранённому значению поля.

## Goals / Non-Goals

**Goals:**

- ключ попадает только в бандл из секрета CI: ни в git, ни в настройки, ни в интерфейс, ни в лог сборки;
- одно место в ядре решает, каким ключом идёт запрос KLIPY и как показать отказ встроенного ключа.

**Non-Goals:**

- встроенный ключ GIPHY: бесплатный общий ключ упрётся в 100 запросов в час на всех, продовый — платный;
- ротация ключа без релиза, удалённый конфиг, прокси для KLIPY;
- смена порядка источников: со своим ключом GIPHY первым остаётся GIPHY, как сейчас.

## Decisions

**1. Подстановка — второй `define` рядом с токеном.** `common.define` в `build.mjs` получает
`__KLIPY_API_KEY__: JSON.stringify(klipyKey)`. Объявление — `declare const __KLIPY_API_KEY__: string` в
`src/types.d.ts`, в `vitest.config.ts` — пустая строка. Читает константу один модуль — новый
`src/core/builtinKlipyKey.ts` (`BUILTIN_KLIPY_KEY`). Отдельный модуль, а не вторая константа в `builtinToken.ts`: тесты
подменяют модуль `vi.mock` целиком, и тесту GIF не нужно знать о токене Telegram, а `builtinToken.ts` по смыслу — о
боте. Объединять оба в `builtin.ts` — рефактор вне задачи.

**2. Проверка формата — `readKlipyKey` в `scripts/klipyKey.ts`.** Пусто или `undefined` — `''`; пробелы и переводы
строки по краям снимаются; значение не `^[\w-]+$` — `Error` о формате без значения. Формат ключа KLIPY не опубликован
(тестовый ключ — 64 символа `[A-Za-z0-9]`), поэтому проверка мягкая: ловит пробел, кавычку или перевод строки внутри
вставки, но не длину и не алфавит. Строгая проверка рисковала бы уронить релиз на продовом ключе другого вида.
`build.mjs` печатает «встроенный ключ KLIPY: есть / нет». Тест — `tests/klipyKey.test.ts`.

**3. Выбор ключа — в `sources/gifs.ts`.** Одна функция `klipyKeyOf(ownKey)` → `{ key, isBuiltin }`
(`ownKey || BUILTIN_KLIPY_KEY`, `isBuiltin: !ownKey`) — и для `availableFeeds` (источник есть, если ключ непустой), и
для `fetchGifs`. Сигнатуры `availableFeeds` и `fetchGifs` не меняются: им по-прежнему приходят `Settings`, а встроенный
ключ — знание модуля источников, а не хуков UI. `checkGifKey` встроенного ключа не касается: проверяется только
введённое в поле.

**4. Отказ встроенного ключа — по статусу из текста ошибки.** В `klipy()` при `isBuiltin` запрос оборачивается:
`httpStatus(error)` из `KEY_REJECT_STATUSES.klipy` или 429 → `new Error(t('error.gifs.builtinUnavailable'))`,
остальное пробрасывается как есть. Ошибка создаётся в мире страницы, через границу SW не идёт, поэтому достаточно
`Error` с текстом на текущем языке, а не `LocalizedError`: в Telegram `LocalizedError` нужен, чтобы цикл импорта узнал
отказ по ключу и остановился, у ленты GIF такого цикла нет. Строка — парой в `RU` и `EN`, текст для статуса с
префиксом «GIF:» и для пустой ленты («Не удалось загрузить GIF: …»): «Встроенный ключ KLIPY недоступен — укажите свой в
настройках». Перехода на GIPHY при отказе нет: источник выбирает пользователь.

**5. Настройки не знают о встроенном ключе.** `DEFAULT_SETTINGS.klipyKey` остаётся `''`. Тексты поля и группы
выбирает чистая функция `klipyKeyText(hasBuiltinKey)` рядом с `telegramTokenText/` — константой модуля
`SettingsView`, как у токена: встроенный ключ сборки не меняется до перезагрузки. Со встроенным: подпись
`settings.klipy.labelOptional` («Свой KLIPY API key (необязательно)»), подсказка `settings.klipy.whereOptional`
(поиск работает без ключа, свой — если встроенный недоступен; ссылка на Partner Panel), пояснение группы
`settings.gif.builtinNote` (поиск KLIPY без ключа, ключ GIPHY добавит источники GIPHY; ссылка на доку). Без
встроенного — прежние литерал «KLIPY API key», `settings.klipy.where` и `settings.gif.oneKey`. Подпись — ключ словаря
или `null` для литерала: «KLIPY API key» одинакова на обоих языках и в словарь не заводится.

**6. CI.** `ci.yml`: `KLIPY_API_KEY` в `workflow_call.secrets` и `env` шага `pnpm build`; `release.yml` передаёт секрет
явно рядом с `TELEGRAM_BOT_TOKEN`. Незаданный секрет — пустая строка и сборка без ключа.

**7. Стенд.** `dev/harness-server.mjs` и `.env` (`KLIPY_KEY`) не меняются: они кладут свой ключ в настройки стенда.
Встроенный ключ на стенде — сборка `KLIPY_API_KEY=… pnpm watch` при пустом `KLIPY_KEY` в `.env`. Имя переменной сборки
отличается от `KLIPY_KEY` стенда намеренно: одна переменная для обоих путей сделала бы на стенде ключ одновременно
встроенным и своим, и путь встроенного ключа не проверялся бы.

## Risks / Trade-offs

- [Ключ достают из бандла и тратят от имени amo stickers] → продовый ключ KLIPY рассчитан на клиентский код и без
  лимита; при блокировке — новый ключ в Partner Panel, новый секрет и патч-релиз; пользователь не ждёт релиза — ошибка
  отказа ведёт его к своему ключу.
- [Поисковые запросы всех пользователей идут к KLIPY без их согласия на ключ] → KLIPY и так был источником поиска;
  политика конфиденциальности и дока говорят о встроенном ключе.
- [Разбор статуса из текста ошибки] → формат и разбор в одном модуле `net.ts`, тест на пару уже есть.
- [Релиз выйдет без ключа, если секрет не заведён] → поведение как сейчас; строка «встроенный ключ KLIPY: нет» в логе
  сборки показывает это.

## Migration Plan

1. Владелец репозитория получает продовый ключ KLIPY в Partner Panel и заводит секрет: `gh secret set KLIPY_API_KEY`.
2. Мерж PR — без релиза; ключ выйдет пользователю PR релиза (минор). Без секрета релиз выходит без ключа.
3. Откат: удалить секрет или выпустить новый ключ — следующий релиз без ключа или с новым; настройки пользователей не
   меняются.

## Open Questions

- Условия продового ключа KLIPY (обязательные параметры запроса, требования к атрибуции сверх «Powered by KLIPY»)
  проверяются при его получении в Partner Panel; если они потребуют правок запросов, это отдельная задача.
