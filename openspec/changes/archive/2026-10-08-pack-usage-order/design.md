## Context

Паки читает `listPacks` (`src/core/db.ts`) — все записи хранилища `packs`, отсортированные по `createdAt`; у «Моих
стикеров» `createdAt: 0`, поэтому они первые. Провайдер пикера держит список в `packs` (`usePickerState`) и
перечитывает его `refreshPacks`: на каждое открытие попапа (`useOpenLoad`), после импорта, сохранения своего стикера,
удаления стикера и пака. Лента и полоса вкладок строятся из `packs` в его порядке (`feedSections`), раздел «Недавние»
добавляется перед ними.

Отправка: ячейка (`StickerCell` → `useCellSend`) зовёт `send(item)` провайдера, он — `onSend` фасада (`app.ts`:
файл, отправка, `pushRecent`), затем закрывает попап. `SendItem` стикера — `{ kind: 'local', stickerId }`; из какого
раздела нажали, он не знает, и он же хранится в недавних.

Импорт (`importTelegramSet`, `sources/telegram.ts`) пишет пак новой записью с `createdAt: Date.now()` и
перезаписывает её при повторном импорте; стикеры получают `createdAt: pack.createdAt + index`. Отмена и неудача
возвращают прежнюю запись пака.

## Goals / Non-Goals

**Goals:**

- Порядок паков Telegram по последнему использованию одной чистой функцией с тестом.
- Снимок порядка на открытие попапа: внутри открытого попапа порядок не прыгает.
- Ни миграции, ни смены версии IndexedDB.

**Non-Goals:**

- Синхронизация порядка между устройствами и браузерами: библиотека локальна.
- Ручная перестановка и выключатель — #104.

## Decisions

### Поле `usedAt` в записи пака

`Pack.usedAt?: number` — время последнего использования (мс). Хранилище паков по `keyPath: 'id'`, необязательное поле
не требует `onupgradeneeded`: старые записи читаются без него, и пак без поля — «не использован». Удаление пака
удаляет запись, а с ней и поле.

Альтернатива — отдельное хранилище статистики: нужна новая версия БД и миграция, удаление пака пришлось бы
синхронизировать с ним. Отвергнута.

Альтернатива — frecency (`score` + `scoreAt` с затуханием и гистерезисом, как предлагал issue): решили MRU, как в
Telegram — одна отметка, без констант, которые надо подбирать, и предсказуемо для пользователя («последний — первый»).

### Отметка использования — `touchPack(packId)` в `db.ts`

Читает запись и пишет её с `usedAt: Date.now()` одной `readwrite`-транзакцией: запись пака из импорта в другой
вкладке между чтением и записью не потеряется. Пака нет (удалён в другой вкладке) — ничего не пишет и не бросает.

Зовёт её провайдер, а не `app.ts`: только UI знает, из какого раздела нажали. `send(item, packId?)` провайдера после
успешного `onSend` вызывает `touchPack(packId)`, если `packId` передан. Сбой записи — `console.warn`, без статуса:
стикер уже отправлен, а ошибка порядка поверх «отправлено» сбила бы с толку. Сигнатура `onSend` фасада не меняется.

`packId` передаёт ряд ленты (`FeedRow`): у раздела пака — его id, у «Недавних» — ничего. Ячейка
(`StickerCell`) пробрасывает его в `useCellSend(item, packId)`. `SendItem` не расширяется: он хранится в недавних, и
раздел нажатия в нём был бы ложным для повторной отправки из «Недавних».

Отметка для «Моих стикеров» тоже пишется — порядок их не двигает (функция порядка ставит их первыми), а условие «не
отмечать свой пак» было бы лишней веткой.

### Чистая функция порядка — `orderPacks(packs, snapshot)`

Файл `src/core/packOrder.ts` (рядом с `db.ts`, без DOM и IndexedDB), тест — `tests/packOrder.test.ts`.

- Свой пак (`source: 'custom'`) — первым.
- `snapshot === null` (открытие попапа): паки Telegram по `usedAt` по убыванию; без `usedAt` — после, по `createdAt`;
  равные `usedAt` — по `createdAt`.
- `snapshot` — массив id паков Telegram в показанном порядке: паки не из снимка (появились в открытом попапе) идут
  первыми, между собой — тем же правилом, затем паки снимка в порядке снимка; id снимка, которых больше нет, пропускаются.

Возвращает новый массив паков и не меняет вход. Снимок выводится из результата (id паков Telegram по порядку).

`listPacks` остаётся «все записи по `createdAt`» — сортировка по использованию — дело пикера, а не хранилища.

### Снимок в провайдере

`usePickerState` держит снимок в `ref` (не в состоянии: он не нужен рендеру). `refreshPacks` получает режим:
`refreshPacks({ isReorder: true })` — только из `useOpenLoad` на открытие: порядок считается заново, снимок
обновляется. Без опции — все остальные вызовы (импорт, сохранение, удаление): порядок по текущему снимку. Так любое
перечитывание внутри открытого попапа порядок не меняет, а новый пак встаёт первым — как и при следующем открытии.

Альтернатива — сбрасывать снимок по закрытию попапа: открытие — не единственная точка, где фасад перечитывает паки,
и порядок зависел бы от гонки закрытия и перечитывания. Явный флаг у вызова на открытие проще проверить.

### Импорт

Новый пак — `usedAt: Date.now()`: первым, как в Telegram. Повторный импорт — запись пака берёт `createdAt` и `usedAt`
из прежней записи: место пака не меняется, в том числе у пака без использования (сейчас `createdAt` перезаписывается,
и пак уезжал бы в конец неиспользованных). Порядок стикеров внутри пака не зависит от `createdAt` пака: стикеры
получают `createdAt` от времени начала импорта плюс индекс, как раньше от `pack.createdAt`. Откат отмены и неудача
возвращают прежнюю запись целиком — с её `usedAt`.

## Risks / Trade-offs

- [Отправка закрывает попап до записи `usedAt`, быстрое повторное открытие прочитает старый порядок] → запись — одна
  транзакция после отправки, открытие после неё её увидит; гонка в доли секунды даёт лишь прежний порядок до следующего
  открытия.
- [Порядок пляшет у тех, кто чередует несколько паков] → это поведение Telegram «Dynamic Pack Order»; выключатель и
  ручной порядок — #104.
- [Повторный импорт с прежним `createdAt` пака меняет основу `createdAt` стикеров] → основа — время начала импорта,
  та же, что сейчас (`Date.now()` при импорте); порядок стикеров пака не меняется.

## Migration Plan

Не нужна: поле необязательное, версия БД та же. Откат версии расширения оставит поле в записях, прежний код его
игнорирует.
