## Context

`src/` — 490 файлов TS/TSX в ~200 каталогах. Плоские области (`src/core`, `src/core/ui`, `src/shared`, `src/page`,
`src/extension`, `src/userscript`) держат файлы рядом, а UI пикера (`src/core/ui/Picker/**`) и подмодули ядра
(`i18n/`, `libraryFile/`, `sources/`, `zip/`, `ui/renderMessage/`) — по каталогу на компонент, хук или подмодуль.
Сборка — esbuild (IIFE, четыре точки входа и два вложенных бандла строкой), тесты — vitest 5 на vite 8, проверка
типов — TS 7 (tsgo), eslint — typescript-eslint с `no-restricted-imports` для границ ядра, `shared` и агента. Тесты
сознательно не грузят виртуальные модули `gif-worker:code` и `page-agent:code` и `lottie-web` без подмены.

## Goals / Non-Goals

**Goals:**

- один источник alias — `paths` в `tsconfig.json`, остальные инструменты берут их оттуда или сверяются с ним;
- граница модуля видна в импорте и проверяется автоматически (eslint и тест структуры);
- бандлы по составу как до правки.

**Non-Goals:**

- перенос файлов между каталогами, переименования, правка логики — кроме устранения циклов, если barrel их создаст;
- barrel у плоских областей и общий barrel ядра;
- `docs/` (отдельный пакет) и `.mjs` вне проверки типов (`build.mjs`, `scripts/*.mjs`, `dev/`).

## Decisions

**Схема alias — по областям** (выбор пользователя): `@core/*`, `@ui` / `@ui/*` (= `src/core/ui/Picker`), `@shared/*`,
`@page/*`, `@extension/*`, `@userscript/*`, `@scripts/*`, `@tests/*`. `paths` без `baseUrl` (пути от `./`): TS 7
`baseUrl` не требует. Альтернатива — один `@/*` → `src/*`: короче конфиг, но длиннее импорты UI
(`@/core/ui/Picker/...`).

**Модуль — каталог с кодом вне плоских областей.** Barrel модуля реэкспортирует только свои файлы:
`export * from './X'`, для `*.types.ts` — `export type * from './X.types'`; дочерние модули он не реэкспортирует —
иначе barrel родителя тянул бы всё поддерево и давал циклы. Конфликт имён двух `export *` TS ловит ошибкой (TS2308) и
решается явным реэкспортом. Альтернатива — явные именованные списки: точнее, но 180 файлов ручного API, который
разъезжается с кодом.

**Куда ведёт импорт** — по положению цели относительно каталога импортирующего файла:

| Цель | Импорт |
|---|---|
| файл того же каталога | `./X` |
| модуль ниже по дереву | `./child` или `./a/b` — путь к каталогу модуля (его barrel) |
| модуль в другом месте | `@ui/...` / `@core/...` — каталог модуля (barrel) |
| файл плоской области в другом каталоге | `@core/sender`, `@shared/pageBridge`, `@core/ui/createPicker` |

Свой barrel изнутри модуля не импортируется. Импорт родительского модуля из дочернего (`feedSections` → типы
`StickersMode`) идёт через barrel родителя: в рантайме цикла нет, пока импорт типовой (`import type` стирается
`verbatimModuleSyntax`); циклы значений ищет проверка ниже.

**Перевод импортов — codemod, а не руками.** Скрипт в scratchpad (не в репозитории): разбирает спецификаторы
`import` / `export … from` / `vi.mock` / `import()`, разрешает их в файл, выбирает форму по таблице выше и пишет
barrel-ы. Затем `eslint --fix` (порядок импортов) и `prettier`. `vi.mock` указывает на файлы плоской области
(`@core/convert`, `@core/db`, …) — они и остаются файлами: подмена barrel не задела бы импорт изнутри модуля.

**Конфиги.**

- `tsconfig.json` — `paths`.
- esbuild читает `paths` из `tsconfig.json` сам, в том числе во вложенных бандлах `bundleCodePlugin`; `build.mjs`
  правится, только если сборка их не подхватит.
- `vitest.config.ts` — `resolve.alias` из тех же `paths` (импорт `tsconfig.json`, перевод шаблонов в регулярные
  выражения), а не копия списка: новый alias в `tsconfig.json` не разъедется с тестами. Встроенное `tsconfigPaths`
  vite 8 — если оно есть и работает в проекте `unit`, берётся оно.
- `eslint.config.mjs`: группа `simple-import-sort` `^@(core|ui|shared|page|extension|userscript|scripts|tests)(/|$)`
  вместо `^@/`; в `src/**` — запрет `^\.\./` и `^@core/ui/Picker(/|$)`; граница ядра — `^@(userscript|extension)/`,
  `shared` — любой alias, кроме `@shared/`, `page` — любой alias, кроме `@page/` и `@shared/`. Импорты тестов не
  ограничиваются: `../build.mjs?raw` и `../docs/...` остаются относительными.

**Тест структуры** (`tests/moduleStructure.test.ts`): `import.meta.glob` с `?raw` по `src/**/*.{ts,tsx}` и
`tests/**/*.ts` — у каждого каталога-модуля есть `index.ts`, каждый alias-спецификатор ведёт в каталог с `index.ts` или
в файл плоской области, а не в файл внутри модуля. Node API тесту не нужен. eslint без плагина файловой системы
этого не проверит: по строке пути не видно, файл это или каталог.

## Risks / Trade-offs

- [barrel тянет соседние файлы модуля, и тест грузит то, чего раньше не грузил: `@core/sources` → `telegram.ts` →
  `convert.ts` → `gif-worker:code` и `lottie-web`] → тест подменяет `@core/convert` `vi.mock`, как уже делает
  `telegram.test.ts`; если таких мест много — заглушка виртуальных модулей в `vitest.config.ts`.
- [цикл значений через barrel: модуль A берёт barrel B, а B — barrel A] → после codemod поиск циклов по графу
  значимых импортов (без `import type`) скриптом; цикл рвётся импортом типа или переносом общей константы в нижний
  модуль.
- [tree-shaking: barrel втягивает в бандл неиспользуемые модули с побочными эффектами] → сравнение бандлов с базой
  до правки: размер и наличие токена, ключа, кода Worker-а по файлам; модули ядра без побочных эффектов при импорте.
- [большой дифф, конфликт с параллельными ветками] → отдельный PR без правок логики; ветки после мержа
  переводятся тем же codemod.

## Migration Plan

Codemod одной группой, проверка (`pnpm lint`, `pnpm test`, `pnpm build`, сравнение бандлов), ручная проверка на
стенде. Откат — revert одного squash-коммита.
