## Context

Мотивация — proposal.md. Сейчас:

- `release.yml` на каждый push в `master` гоняет `ci.yml`, читает версию из `package.json` и выпускает релиз, только
  если тега `v<версия>` ещё нет; иначе — `::warning::` и зелёный прогон. Механизм «нет подъёма — нет релиза» уже есть,
  мешает только требование подъёма в каждом PR.
- `scripts/check-version.mjs` сверяет версию в трёх местах (`package.json`, `src/extension/manifest.json`, литерал
  `@version` в `build.mjs`) и с `--base` требует рост версии, если PR трогает `PRODUCT_PATHS`.
- `build.mjs` уже читает `src/extension/manifest.json` и пишет в `dist/extension/manifest.json` с правкой `matches`.
- `pages.yml` запускается push-ем в `master` по путям доки и вручную.
- Релиз создаётся `GITHUB_TOKEN`-ом, а событие `release` от `GITHUB_TOKEN` других workflow не запускает.

## Goals / Non-Goals

**Goals:**
- Подъём версии — правка одного поля `package.json`.
- Публикация доки привязана к выпуску релиза.

**Non-Goals:**
- Автоматика сборки релиза (changesets, release-please, кнопка с выбором уровня): уровень решает человек в PR релиза.
- Метки уровня на PR и категории заметок релиза.
- Изменения `chrome-web-store.yml` и логики публикации в стор: он по-прежнему идёт за выпущенным релизом.

## Decisions

### Версия — из `package.json` при сборке
`build.mjs` читает `package.json` и ставит `manifest.version` перед записью `dist/extension/manifest.json`, а строку
`@version` заголовка собирает из той же переменной. Из `src/extension/manifest.json` поле `version` удаляется: оставить
его — значит оставить второе место, которое молча разойдётся (сборка его перезапишет, а человек увидит старое число).
Исходный manifest напрямую в Chrome не грузится — грузится собранный, — поэтому поле в исходнике не нужно.

Альтернатива — синхронизация трёх мест скриптом (`pnpm version` + хук): три места остаются, проверка совпадения
тоже, выигрыша нет.

### Проверка версии: формат и «не ниже базы»
`check-version.mjs` всегда разбирает версию `package.json` (`parseVersion`) — ловит битый формат до того, как Chrome
откажет в manifest. С `--base` сравнивает с версией `package.json` базы: ниже — ошибка, равна или выше — проходит.
Разбор изменённых путей и `PRODUCT_PATHS` больше не нужен: от путей ничего не зависит. `checkVersionGrowth` заменяется
на `checkVersionNotLower`, `checkVersionConsistency`, `readBannerVersion`, `hasProductChanges` и тип `VersionSource`
удаляются вместе с тестами.

Список файлов продукта остаётся в тексте правил (`task-workflow`, `CLAUDE.md`): по нему решается, нужна ли задаче
спека OpenSpec, а не версия.

Альтернатива — требовать рост, только если PR меняет версию: «меняет и не выше» — то же самое, что «ниже», раз равная
версия значит «не менял».

### Мерж без подъёма — `::notice::`
Ветка «тег есть» в `release.yml` пишет `::notice::` вместо `::warning::`: это теперь обычный исход мержа, и
предупреждение на каждом прогоне приучило бы его не читать.

### Дока — `workflow_call` из `release.yml`
Событие `release: published` не подходит: релиз создаёт `GITHUB_TOKEN`, и такое событие workflow не запускает.
Поэтому `pages.yml` получает триггер `workflow_call` (вместе с `workflow_dispatch`), а `release.yml` вызывает его
job-ом за `release` при `released == 'true'` — тем же условием, что и публикацию в стор, так что перезапуск упавшей
попытки того же прогона доку тоже публикует. Вызывающий job выдаёт `pages: write` и `id-token: write`: вызванный
workflow не может получить прав больше, чем у вызывающего job-а.

`concurrency` переезжает с уровня workflow на job `deploy`: группа `pages` по-прежнему не даёт двум публикациям идти
одновременно и не отменяет идущую, а сборка двух прогонов может идти параллельно.

Ручной запуск с другой ветки пропускается условием `github.ref == 'refs/heads/master'` на сборке — как у `release.yml`.

Альтернатива — PAT для создания релиза, чтобы сработал `release: published`: лишний секрет ради того, что
`workflow_call` даёт без него.

### PR релиза — без issue и спеки
PR релиза меняет только `version` в `package.json`; заметки собирает `--generate-notes`. Issue и спека OpenSpec ему
не нужны: требования вошли с PR, которые он выпускает. Ветка — `release/<версия>`. Уровень — наибольший из PR с
прошлого тега по таблице уровней `task-workflow`.

## Risks / Trade-offs

- [Сборка `master` между релизами несёт номер прошлого релиза с другим кодом] → артефакт `build` прогона ставят
  только руками для проверки; `@updateURL` ведёт на `releases/latest`, автообновление у пользователя не задето.
- [Правка доки о выпущенном поведении ждёт релиза] → ручной запуск `pages.yml` из `master`.
- [Правка доки о невыпущенном поведении уйдёт на сайт ручным запуском вместе с исправлением опечатки] → ручной запуск
  публикует весь `master`; при неопубликованных правках доки ждать релиза. Правило записано в `CLAUDE.md`.
- [Срочный фикс выходит вместе со всем накопленным в `master`] → это свойство накопительных релизов; фикс, который
  нельзя выпускать с накопленным, — повод выпустить накопленное раньше.

## Migration Plan

Этот PR сам версию не поднимает: продукт для пользователя не меняется, а проверка версии в PR берётся из ветки PR и
уже не требует подъёма. Следующий релиз — первый PR релиза по новым правилам. Откат — revert PR.
