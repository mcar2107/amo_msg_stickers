## Why

(issue #60)

Бинарные ответы (GIF из поиска, файлы стикеров Telegram) читаются с лимитом размера, а JSON-ответы API и тела ошибок —
целиком. Если GIPHY, KLIPY, Telegram или хост за редиректом в пределах сетевой политики отдадут огромный ответ, он
скачивается и разбирается полностью до того, как появится ошибка: в service worker расширения, в userscript через
менеджер и в userscript без менеджера. Найдено на аудите PR #6 как «вне скоупа».

## What Changes

- JSON-ответ API читается не больше 2 МБ (`MAX_JSON_BYTES` в `core/net.ts`) во всех трёх окружениях. Превышение
  обрывает загрузку, не дочитывая остаток, ошибкой «Файл больше 2 МБ» — той же, что у файлов (`error.net.tooBig`).
  Реальные ответы GIPHY, KLIPY и Telegram — десятки и сотни КБ.
- Тело не-2xx ответа читается не больше, чем нужно для текста ошибки: в ошибку попадают 200 символов, читается не
  больше 800 байт — 200 символов UTF-8 по 4 байта. Остаток не скачивается.
- Обычные ответы работают как раньше: разбор JSON, тексты HTTP-ошибок, лимиты файлов не меняются.

Не входит: новые тексты ошибок, изменение лимитов файлов, подъём версии.

## Capabilities

### New Capabilities

— нет.

### Modified Capabilities

- `runtime-hosts`: требование «Сетевые запросы в обход CORS страницы» — лимит JSON-ответа и ограниченное чтение тела
  ошибки во всех окружениях.

## Impact

- `src/core/net.ts` — `MAX_JSON_BYTES`, чтение JSON с лимитом, ограниченное чтение тела ошибки в `fetchChecked`.
- `src/extension/background.ts` — JSON через чтение с лимитом.
- `src/userscript/fetchNetwork.ts` — то же.
- `src/userscript/gmNetwork.ts` — лимит JSON вместо `NO_LIMIT`, проверка размера текстового тела на `onload`, обрыв
  тела не-2xx ответа по ходу загрузки.
- Тесты: `tests/net.test.ts`, `tests/background.test.ts`, `tests/gmNetwork.test.ts`, новый `tests/fetchNetwork.test.ts`.
