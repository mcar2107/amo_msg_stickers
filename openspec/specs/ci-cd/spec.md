# ci-cd Specification

## Purpose

Автоматические проверки каждого PR в `master` и выпуск релиза с готовым архивом расширения и userscript-ом после
мержа — чтобы в `master` не попадал непроверенный код, а установочные файлы брались из релиза, а не собирались руками.

## Requirements

### Requirement: Проверки PR
Для каждого PR в `master` система SHALL запускать шесть отдельных проверок: линт (eslint и prettier), проверку типов,
юнит-тесты, сборку обеих целей, сборку сайта доки и проверку версии. Каждая проверка MUST отображаться в PR отдельным
статусом, упавшая проверка MUST давать статус «failure». Новый push в ветку PR MUST перезапускать проверки и отменять
незавершённый прогон по предыдущему коммиту.

#### Scenario: Ошибка линта
- **WHEN** в PR попадает файл, не проходящий `prettier --check`
- **THEN** проверка линта в PR падает, остальные проверки выполняются и показывают свой результат

#### Scenario: Упавший тест
- **WHEN** в PR есть падающий юнит-тест
- **THEN** проверка тестов в PR падает

#### Scenario: Битая ссылка в доке
- **WHEN** в PR страница доки ссылается на несуществующую страницу доки
- **THEN** проверка сборки доки в PR падает

#### Scenario: Все проверки зелёные
- **WHEN** код PR проходит линт, типы, тесты, сборку, сборку доки и проверку версии
- **THEN** все шесть проверок в PR успешны

#### Scenario: Новый коммит в PR
- **WHEN** в ветку PR пушится новый коммит, пока проверки предыдущего ещё идут
- **THEN** прогон по предыдущему коммиту отменяется, проверки идут по новому

### Requirement: Согласованность версии
Версия SHALL быть записана одинаково в `package.json`, `src/extension/manifest.json` и в `@version` заголовка
userscript. При расхождении проверка версии MUST падать с сообщением, в котором перечислены все три значения.

#### Scenario: Версия не поднята в манифесте
- **WHEN** в PR `package.json` поднят до `0.4.0`, а `manifest.json` остался `0.3.0`
- **THEN** проверка версии падает, в логе видны все три значения версии и их источники

### Requirement: Рост версии в PR
Для PR в `master`, который меняет файлы продукта, проверка версии SHALL сравнивать версию ветки с версией
`package.json` в `master` и MUST падать, если версия ветки не выше. Версии сравниваются как `MAJOR.MINOR.PATCH` по
числам, а не по строке. Файлы продукта — то, из чего собирается релиз: `src/`, `build.mjs`, `tailwind.config.ts`,
`tsconfig.json`, `package.json`, `pnpm-lock.yaml`. PR, который их не трогает (документация, CI, скрипты, тесты,
OpenSpec), MUST проходить проверку без подъёма версии.

#### Scenario: Версию забыли поднять
- **WHEN** PR меняет файлы продукта, версия в ветке PR равна версии в `master`
- **THEN** проверка версии падает с сообщением, что версию нужно поднять

#### Scenario: PR без изменений продукта
- **WHEN** PR меняет только `CLAUDE.md` и `.github/workflows/ci.yml`, версия в ветке равна версии в `master`
- **THEN** проверка версии проходит, в логе — что подъём версии не нужен

#### Scenario: Числовое сравнение
- **WHEN** в `master` версия `0.9.0`, в PR — `0.10.0`
- **THEN** проверка версии проходит

### Requirement: Сборка PR доступна для установки
Прогон проверок PR SHALL выкладывать артефактом прогона архив расширения и userscript, собранные из коммита PR, —
чтобы изменение можно было поставить руками до мержа.

#### Scenario: Ручная проверка PR
- **WHEN** проверка сборки в PR прошла
- **THEN** на странице прогона доступен артефакт с архивом расширения и `amo-stickers.user.js`

### Requirement: Релиз после мержа в master
После каждого попадания коммита в `master` система SHALL прогнать те же проверки, что и для PR (кроме роста версии),
и только при их успехе создать тег `v<версия>` на этом коммите и GitHub Release с тем же именем. К релизу MUST быть
приложены:

- `amo-stickers.zip` — содержимое `dist/extension` с `manifest.json` в корне архива; имя без версии, чтобы ссылка на
  архив последнего релиза не менялась от версии к версии;
- `amo-stickers.user.js` — userscript.

Заметки релиза MUST формироваться автоматически по PR, вошедшим в релиз со времени предыдущего.

#### Scenario: Мерж PR с новой версией
- **WHEN** PR с версией `0.3.0` мержится в `master`, релиза `v0.3.0` ещё нет
- **THEN** появляется тег `v0.3.0` на коммите мержа и релиз `v0.3.0` с `amo-stickers.zip` и `amo-stickers.user.js`

#### Scenario: Ссылка на последнюю версию
- **WHEN** пользователь открывает `https://github.com/mcar2107/amo_msg_stickers/releases/latest/download/amo-stickers.zip`
- **THEN** скачивается архив расширения из релиза с наибольшей версией

#### Scenario: Установка из релиза
- **WHEN** пользователь скачивает `amo-stickers.zip`, распаковывает и загружает папку как распакованное
  расширение
- **THEN** расширение ставится без ошибок манифеста, его версия в `chrome://extensions` совпадает с версией релиза

#### Scenario: Проверки в master упали
- **WHEN** после мержа в `master` падает любая проверка
- **THEN** тег и релиз не создаются

### Requirement: Повторный релиз той же версии
Если тег `v<версия>` уже существует, выпуск релиза SHALL завершиться успешно без создания тега и релиза и MUST
оставить в прогоне предупреждение, что версия уже выпущена. Существующий релиз и его файлы MUST NOT меняться.

#### Scenario: Перезапуск релиза
- **WHEN** workflow релиза перезапускается на коммите, версия которого уже выпущена
- **THEN** прогон зелёный, в нём предупреждение «версия уже выпущена», релиз `v<версия>` не изменён

#### Scenario: Push в master без подъёма версии
- **WHEN** в `master` попадает коммит, в котором версия не поднята относительно последнего релиза
- **THEN** новый релиз не создаётся, в прогоне предупреждение, что версия уже выпущена

### Requirement: Публикация доки
После попадания в `master` коммита, меняющего исходники доки или её сборку, система SHALL собрать сайт доки и
опубликовать его на GitHub Pages. Публикация MUST NOT зависеть от выпуска релиза и MUST NOT требовать подъёма версии,
если файлы продукта не менялись. Если сборка доки упала, опубликованный сайт MUST остаться прежним.

#### Scenario: Правка текста доки
- **WHEN** в `master` мержится PR, который меняет только исходники доки
- **THEN** сайт доки на Pages обновляется, релиз не создаётся, проверка версии в PR не требовала подъёма

#### Scenario: Сборка доки упала
- **WHEN** после мержа сборка сайта доки падает
- **THEN** на Pages остаётся предыдущая версия сайта

### Requirement: Встроенный токен Telegram-бота в сборке
Сборка SHALL встраивать токен Telegram-бота из переменной окружения `TELEGRAM_BOT_TOKEN` в расширение и userscript.
Сборка в CI SHALL получать его из секрета репозитория `TELEGRAM_BOT_TOKEN`, а релиз MUST выкладывать сборку с ним. Без
переменной сборка MUST проходить и MUST NOT содержать токена. Значение, которое не похоже на токен бота (не
`<цифры>:<строка>`), MUST ронять сборку с ошибкой, в которой нет самого значения. Токен MUST NOT лежать в git и MUST NOT
печататься в логах сборки.

#### Scenario: Релиз
- **WHEN** в `master` мержится PR с новой версией, секрет `TELEGRAM_BOT_TOKEN` задан
- **THEN** в `amo-stickers.zip` и `amo-stickers.user.js` релиза импорт пака работает без своего токена

#### Scenario: Сборка без секрета
- **WHEN** сборка идёт без переменной `TELEGRAM_BOT_TOKEN` — локально, в `pnpm watch` или в PR из форка
- **THEN** сборка проходит, а импорт без своего токена показывает «Укажите токен бота в настройках»

#### Scenario: Битое значение
- **WHEN** переменная `TELEGRAM_BOT_TOKEN` задана строкой не формата `<цифры>:<строка>`
- **THEN** сборка падает с ошибкой о формате токена, значение переменной в выводе не появляется
