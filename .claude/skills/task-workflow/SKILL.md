# Воркфлоу задачи

Одна задача — один issue, одна ветка, один PR. Репозиторий на GitHub, поэтому CLI — `gh` (`glab` здесь не
применяется). Номер issue — сквозной идентификатор: он в имени ветки, в теле PR и в коммитах. Требования и план
задачи, которая меняет файлы продукта, ведутся в OpenSpec (`openspec/changes/<change>`, артефакты на русском).

1. **Issue.** Задача заводится в репозитории до правок — чтобы у PR был предмет, с которым аудит сверяет результат.
   Тело описывает наблюдаемое поведение и критерий готовности, а не план правок.

   Перед созданием — поиск по открытым и закрытым issue: задача может быть уже заведена, и тогда работа идёт в ней, а
   не во второй копии. Закрытая issue о той же задаче — повод переоткрыть её или сослаться на неё в новой, а не
   заводить молча. Запросов — несколько, по разным словам задачи: поиск ищет слова, а не смысл.

   ```bash
   gh issue list --state all --search '<ключевые слова>' --json number,title,state
   ```

   ```bash
   gh issue create --title '<кратко, что должно измениться>' --label enhancement --body '<описание и критерий готовности>'
   ```

   Метки из набора репозитория: `bug`, `enhancement`, `documentation`.

   Связанные issue, найденные поиском, связываются с новой — при создании или позже через `gh issue edit`:

   | Связь | Когда | Создание | Потом |
   |---|---|---|---|
   | родитель | задача — часть большей | `--parent 40` | `--parent 40` |
   | блокирует / блокируется | одну нельзя закончить без другой | `--blocking 45`, `--blocked-by 39` | `--add-blocking`, `--add-blocked-by` |
   | упоминание | общая тема без зависимости | `Связано с #39` в теле | `gh issue comment` |

   Упоминание `#N` GitHub показывает в ленте обеих issue, но зависимостью не считает: для «нельзя без» — только
   `blocked-by`.

   Перед началом работы issue назначается на себя — и свежезаведённая, и взятая из уже открытых: исполнитель виден в
   списке issue, и задачу не возьмут вторым заходом.

   ```bash
   gh issue edit 42 --add-assignee @me
   ```
2. **Ветка от master.** Только от свежего `master`, не от текущей ветки: иначе в PR приедут чужие коммиты.
   Имя — `<type>/<номер issue>-<краткое-имя>`, где `type` — `feature`, `fix`, `chore`, `docs`. Исключение — PR
   релиза: ветка `release/<версия>` без номера issue («Релиз»).

   ```bash
   git switch master && git pull --ff-only
   git switch -c feature/42-preact-picker
   ```
3. **Спека.** Задача, которая меняет файлы продукта, идёт через OpenSpec, в том числе исправление: proposal
   фиксирует, что считается готовым, а архив переносит требование в `openspec/specs`, где его увидит следующая задача.
   Файлы продукта — `src/`, `build.mjs`, `tailwind.config.ts`, `tsconfig.json`, `package.json`, `pnpm-lock.yaml`. Без
   спеки идут только PR, которые файлов продукта не трогают: документация, CI, скрипты, тесты. Исключение — PR
   релиза: он меняет только версию в `package.json` и идёт без спеки («Релиз»).

   Change заводится в ветке задачи до первой правки кода. Имя — kebab-case по сути изменения, без номера issue; номер
   пишется в `proposal.md`: «(issue #42)».

   ```text
   /opsx:propose <имя>
   ```

   Реализация — пользовательский скилл `openspec-run` (`~/.claude/skills/`, не в репозитории): исполнитель и аудитор
   на группу задач, коммит на группу. Без него — `/opsx:apply <имя>`.

   ```text
   /openspec-run <имя>
   ```
4. **Правки и PR.** Правки идут в этой ветке; перед PR — `pnpm lint` и `pnpm test` (гейт коммита их не заменяет:
   `.husky/pre-commit` гоняет vitest только по изменённым файлам). PR привязывается к issue ключевым словом в теле,
   иначе issue придётся закрывать руками.

   **Версию PR не поднимает** — ни правка продукта, ни остальные: правки копятся в `master` и выходят пользователю
   PR релиза («Релиз» ниже). Мерж без подъёма — штатный исход, релиз на нём не выходит. Проверка `version` в CI
   требует только, чтобы версия была в формате `MAJOR.MINOR.PATCH` и не ниже, чем в `master`. Исключение — хотфикс.

   ```bash
   git push -u origin HEAD
   gh pr create --base master --fill --body 'Closes #42

   <что сделано и почему так>'
   ```
5. **Аудит.** Пользовательский скилл `review-staged` (`~/.claude/skills/`, не в репозитории) в режиме «ветка
   против master». Без него аудит идёт вручную по тому же диффу и тем же `.claude/rules/*.md`, с тем же
   требованием к находке: файл, строка, цитата из файла.

   Находки ложатся **inline-комментами в PR** — привязанными к файлу и строке, а не одним общим комментом:
   резолвить на повторном аудите можно только тред, заведённый на строке.

   Тело ревью лежит в файле (`/tmp/review.json`), а не в флагах: у `gh api` нет формы для массива объектов.

   ```json
   {
     "commit_id": "<sha головы ветки>",
     "event": "COMMENT",
     "comments": [
       {"path": "src/core/sender.ts", "line": 42, "side": "RIGHT", "body": "<находка и что с ней делать>"}
     ]
   }
   ```

   ```bash
   gh api --method POST repos/mcar2107/amo_msg_stickers/pulls/<N>/reviews --input /tmp/review.json
   ```

   Один тред — одна находка. `event: COMMENT`, а не `REQUEST_CHANGES`: автор PR и ревьюер здесь одно лицо, и
   GitHub не даёт запросить правки у самого себя.

   `line` берётся только из строк, попавших в дифф PR, — на остальные GitHub отвечает 422. Находка в строке,
   которой дифф не касался (у `review-staged` это `pre_existing`), идёт комментом к файлу целиком
   (`"subject_type": "file"` вместо `line` и `side`) либо в общий тред PR (`gh pr comment`). Общий тред резолву
   на шаге 7 не поддаётся — его закрывает ответ автора.
6. **Правка комментов.** Каждая находка правится отдельно и пушится в ту же ветку. Спорную не правят молча —
   ответ в треде с обоснованием тоже закрывает находку.

   ```bash
   gh api --method POST repos/mcar2107/amo_msg_stickers/pulls/<N>/comments/<databaseId первого коммента треда>/replies -f body='<как поправлено или почему нет>'
   ```

   Ответ идёт на **комментарий**, а не на тред: у REST есть только `databaseId` первого коммента, а резолв (шаг 7)
   просит `id` треда из GraphQL. Оба берутся одним запросом ниже.
7. **Повторный аудит и резолв.** Тот же `review-staged` по обновлённой ветке. Резолвится только тред, правка
   которого подтверждена в коде: «ответил» и «поправил» — разные вещи. Резолв идёт через GraphQL — у REST такой
   операции нет.

   ```bash
   # нерезолвнутые треды с путями и строками
   gh api graphql -f query='query($owner:String!,$repo:String!,$pr:Int!){repository(owner:$owner,name:$repo){pullRequest(number:$pr){reviewThreads(first:100){nodes{id isResolved path line comments(first:1){nodes{databaseId body}}}}}}}' \
     -F owner=mcar2107 -F repo=amo_msg_stickers -F pr=<N> --jq '.data.repository.pullRequest.reviewThreads.nodes[] | select(.isResolved | not) | {id, path, line, commentId: .comments.nodes[0].databaseId}'

   gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -F id=<id треда>
   ```

   Находки, всплывшие на повторном аудите заново, — новые треды: шаги 6 и 7 повторяются, пока нерезолвнутых не
   останется.
8. **Архив спеки.** Задача, которая шла через OpenSpec, архивируется до мержа, в той же ветке: `/opsx:archive
   <change>` переносит дельту в `openspec/specs` и change — в `openspec/changes/archive/`, коммит пушится в PR.
   Так требования и код попадают в `master` одним коммитом. Архив после мержа потребовал бы отдельной ветки и PR.
9. **Мерж** — после архива: squash, чтобы в `master` от задачи остался один коммит, и с удалением ветки — issue
   закроется сама по `Closes` из тела PR.

   ```bash
   gh pr merge <N> --squash --delete-branch
   ```

## Релиз

Мерж в `master` выпускает релиз, если тега `v<версия>` для версии из `package.json` ещё нет: `release.yml` ставит
тег `v<версия>`, собирает GitHub Release с заметками по всем PR со времени прошлого релиза, публикует его в Chrome Web
Store и доку на GitHub Pages. Версия записана в одном месте — поле `version` в `package.json`; manifest и заголовок
userscript получают её при сборке.

**PR релиза** выпускает накопленное в `master`. Issue и спека OpenSpec ему не нужны: требования вошли с PR, которые он
выпускает. Ветка — `release/<версия>` от свежего `master`, правка — только версия в `package.json`
(`pnpm version <версия> --no-git-tag-version`, на чистом дереве — иначе pnpm откажет). Заметки собирает
`--generate-notes`, в теле PR достаточно списка выпускаемых PR.

PR, вошедшие в `master` со времени прошлого релиза:

```bash
git fetch --tags
tag=$(gh release view --json tagName --jq .tagName)
gh pr list --state merged --base master --limit 1000 --search "merged:>$(git log -1 --format=%cI "${tag}")" --json number,title,headRefName
```

**Уровень** — наибольший из этих PR, по тому, что получает пользователь:

| Уровень | Когда | Пример |
|---|---|---|
| мажор, минор и патч обнуляются | несовместимое изменение | смена схемы IndexedDB без миграции, переделка продукта |
| минор, патч обнуляется | новое поведение, видимое пользователю | новая функция, источник GIF, настройка |
| патч | продукт меняется, поведение — нет | исправление, рефактор, производительность, зависимости |
| без релиза | файлы продукта не менялись | документация, CI, скрипты, тесты, OpenSpec |

Тип ветки подсказывает уровень PR: `feature` — минор, `fix` и `chore` — патч, `docs` — без релиза; решает всё же
содержимое PR. Уровень CI не проверяет — он на авторе PR релиза.

```bash
git switch master && git pull --ff-only
git switch -c release/0.19.0
pnpm version 0.19.0 --no-git-tag-version
git commit -am 'Релиз 0.19.0'
git push -u origin HEAD
gh pr create --base master --title 'Релиз 0.19.0' --body '<выпускаемые PR>'
```

**Хотфикс** — исправление, которое нельзя ждать до PR релиза: обычный PR задачи (шаги 1–9), который сам поднимает
версию — патч от последнего тега. Его мерж выпускает релиз со всем, что уже накоплено в `master`; если накопленное
выпускать нельзя, сначала решается его судьба, а не хотфикс в обход.

**Дока** публикуется с релизом. Правку доки об уже выпущенном поведении, смерженную без релиза, публикует ручной
запуск — он берёт весь `master`, поэтому только когда в `master` нет правок доки о ещё не выпущенном:

```bash
gh workflow run pages.yml --ref master
```
